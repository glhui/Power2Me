# Skill 设计指南

## 基本理解

Skill 是可复用的工作流包，不只是一个很长的 prompt，也不会凭空增加模型能力。

```text
模型       负责推理和生成
Skill      提供可复用流程与判断指导
工具       观察或操作外部世界
参考资料   提供按需加载的领域知识
脚本       执行重复且需要确定性的操作
资源       提供可复制或改造的输出材料
```

## 设计前需要回答的问题

1. Skill 服务什么可识别的用户目标？
2. 哪些请求应该触发它？
3. 哪些相似请求不应该触发它？
4. 必需输入是什么？
5. 预期输出或状态变化是什么？
6. 哪些事实不得自行推断？
7. 何时必须询问、停止或请求批准？
8. 如何观察是否成功？

## 把信息放到正确位置

| 信息 | 位置 |
|---|---|
| 触发条件、核心流程、关键边界 | `SKILL.md` |
| 详细领域知识或条件性流程 | `references/` |
| 重复且需要确定性的计算或转换 | `scripts/` |
| 输出中需要复制或改造的模板和材料 | `assets/` |
| 整个仓库都适用的工作约定 | 根目录 `AGENTS.md` |
| 单次任务的临时状态 | 任务笔记或工作文件 |
| 持续变化的学习者画像 | 独立学习数据，不放入可复用 Skill |

## 质量信号

好的 Skill 应当：

- 只服务一个可识别目标；
- 能从名称和描述判断何时使用；
- 明确输入、输出和边界；
- 足够简洁，使重要指令不会被淹没；
- 在需要判断时保留灵活性，在错误代价高时足够严格；
- 通过行为而不是固定措辞进行测试；
- 根据证据而不是猜测维护。

## 常见失败方式

- 描述过宽，导致 Skill 到处触发。
- 重复模型本来就知道的通用建议。
- 把一次失败变成永久通用规则。
- `SKILL.md` 逐渐成为混合多个模式的长篇手册。
- 已有工具能可靠完成，却额外增加脚本。
- 把个人状态或项目状态误当成可复用流程。
- 未明确授权边界就修改文件或外部系统。
- 评估只检查标题和措辞，不检查实际行为。
